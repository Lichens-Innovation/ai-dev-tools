# Fold `maestro-core` into the Maestro app

## Context

`packages/maestro-core` was extracted in M1 for a reason that expires. The stated purpose was
"the same code serving two consumers that cannot share a runtime" — the desktop app and the
plugin's standalone hook scripts. But the second of those is not a runtime consumer at all: the
hook scripts get **generated CJS bundles**, not imports. And once M6 folds help-server into the
desktop app, there is exactly one workspace package that imports `@repo/maestro-core`.

A shared package with one consumer is not shared code. It is a directory with extra ceremony:
its own `package.json`, `tsconfig.json`, `vitest.config.ts`, a workspace dependency edge, a
published-export surface to maintain, and a `pnpm install` every time it changes.

**Outcome:** the node-side logic lives at `apps/maestro/src/core/`, the app has one test suite
instead of two, and the plugin's generated libs keep being generated — from the new location.

## The objection, stated honestly

The plugin's `scripts/lib/maestro-session.cjs` and `maestro-skill-regions.cjs` **are** a second
consumer, and they will still exist after M6. They run under bare `node` inside a user's project,
with no `node_modules`, entirely independently of the desktop app.

That does not justify a separate package, because the coupling is at **build time**, not run time.
`esbuild` does not care whether its entry point lives in `packages/` or `apps/`. The bundles are
committed artifacts; the app is where they are produced from.

What it *does* mean: **`build:plugin-libs` is the one thing this refactor can genuinely break**,
and it breaks quietly — the committed `.cjs` files keep working, so nothing fails until someone
edits `success-path.ts` and the plugin silently keeps the old behaviour. Treat the build script as
the load-bearing part of the move, not an afterthought.

---

## Approach

### Target layout

```
apps/maestro/
  src/core/                 ← was packages/maestro-core/src/
    contracts.ts            ← the renderer-safe boundary (see below)
    types.ts  config.ts  render.ts  rules.ts  save.ts  seed.ts
    success-path.ts  skill-regions.ts  session-runtime.ts
    session-log.ts  discovery.ts  tasks.ts  fs-scan.ts
    install.ts  detect.ts   ← added by M3
    scaffold.ts             ← added by M4
    plugin-entries/         ← esbuild entry points for the generated libs
  scripts/build-plugin-libs.mjs
  test/core/                ← was packages/maestro-core/test/
    fixtures/legacy/        ← the parity snapshots; move verbatim
```

`@repo/claude-fs` **stays a package**. It is genuinely shared — help-server uses it heavily, and it
has nothing to do with Maestro.

### The part that needs care: the contracts boundary

Today `contracts.ts` is enforced by a package export: the renderer imports
`@repo/maestro-core/contracts`, and importing the barrel instead would be an obvious, reviewable
mistake. After the move both are just relative paths into `../core/`, and the difference between
`../core/contracts` and `../core/index` is one word in an import line.

This is a real regression in safety and must be replaced with an explicit check. Options, in order
of preference:

1. **A test** asserting no file under `src/renderer/`, `src/preload/`, or `src/shared/` imports
   from `src/core/` except `src/core/contracts`. Cheap, no new tooling, fails loudly.
2. An ESLint `no-restricted-imports` rule with path patterns.
3. A `tsconfig` path alias (`#contracts`) that only maps the safe module — but nothing stops a
   relative import bypassing it, so this is weaker than it looks.

Do option 1 at minimum. Review item 4 in `review-m1-m2.md` already recommends this test *before*
the move; if it exists by then, this step is just updating its paths.

### Migration steps

1. `git mv packages/maestro-core/src apps/maestro/src/core` and
   `git mv packages/maestro-core/test apps/maestro/test/core` — as a **pure move commit**, no edits,
   so the diff is reviewable.
2. Rewrite imports: `@repo/maestro-core` → `../core/index.js` in `main/ipc.ts`;
   `@repo/maestro-core/contracts` → `../core/contracts.js` in `shared/ipc.ts`.
3. Move `build-plugin-libs.mjs` to `apps/maestro/scripts/`, fix its `pkgRoot`/`outDir` resolution,
   and add `"build:plugin-libs"` to the app's scripts.
4. Merge the two vitest configs. `apps/maestro/vitest.config.ts` already exists; widen `include` to
   `["test/**/*.test.ts"]` so it picks up `test/core/`.
5. Delete `packages/maestro-core/` (`package.json`, `tsconfig.json`, `vitest.config.ts`, `README.md`)
   and remove the workspace dependency from `apps/maestro/package.json`.
6. Fold the package README into `apps/maestro/CLAUDE.md` — especially the "generated plugin libs —
   do not hand-edit" warning, which is the highest-value paragraph in it.
7. Update the `GENERATED by …` banner in both `.cjs` files to the new script path. Stale
   provenance comments are worse than none: they send the next person to a directory that no
   longer exists.
8. Fix `apps/ai-tools-manager/CLAUDE.md`'s pointer to `packages/maestro-core/` (added in M1) —
   or skip if M5 already deleted that file.

### `import.meta.dirname` moves too

`discovery.ts`'s `defaultBundledAgentsDir()` resolves
`import.meta.dirname/../../../plugins/ai-tools-manager/agents`. The depth changes with the move,
**and** it is already suspect under bundling (see review item 10 — after electron-vite bundles
main, `import.meta.dirname` is the build output directory). Fix both at once: resolve from
`app.getAppPath()` in the main process and pass the directory in, or set
`MAESTRO_BUNDLED_AGENTS_DIR`. Do not just decrement the `../`s.

## Sequencing

**After M5, before M6.** After M5 because that is when `apps/ai-tools-manager` is deleted and
nothing else could plausibly consume the package. Before M6 because help-server's node logic should
land in the final structure directly rather than being written into `packages/` and moved a week
later.

## Verification

1. **The move commit is pure.** `git show --stat` on step 1 shows renames only, zero content changes.
2. `pnpm --filter maestro test` runs **all 66+** tests (58 core + 8 isolation) from one suite.
3. `pnpm --filter maestro typecheck` clean on both tsconfig projects.
4. **The generated libs are byte-identical across the move.** Run `build:plugin-libs` from the new
   location and confirm `git diff plugins/ai-tools-manager/scripts/lib/` shows **only** the banner
   path change. Anything else means the bundle changed and the hooks' behaviour may have too.
5. **The hooks still run.** Re-run the M1 smoke test: `maestro-inject-agent-context.js` against a
   scratch project must still resolve the success route through a `human_review` node and inject
   the handoff protocol.
6. **The boundary test fails when it should.** Deliberately add
   `import { readConfig } from "../core/index.js"` to a renderer file and confirm the test catches
   it. A guard that has never been seen to fail is not a guard.
7. `pnpm install` at the root leaves a clean lockfile with no dangling `@repo/maestro-core` edge.
