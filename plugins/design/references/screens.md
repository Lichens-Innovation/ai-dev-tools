# Screens

A screen (a page of the app) comes to Claude Design as a **mockup**: a page rebuilt from the
synced components, with sample data, that looks like the running screen. Nothing in the app
changes for it: no stories, no mocks, no view split. The components are the real ones; the page
layout is a hand-made copy, close but not exact.

| Project files                   | Written by       | Role                                                            |
| ------------------------------- | ---------------- | --------------------------------------------------------------- |
| `screens/<name>.html`           | `design-refresh` | Reference: the screen as the code renders it now                |
| `screens/index.json`            | `design-refresh` | The navbar's Pages list (`{ "screens": [{ "name", "path" }] }`) |
| `proposals/screens/<name>.html` | Claude Design    | Target: the mockup plus the change                              |

`design-refresh` writes and rebuilds the mockup when the screen's code
changes. `design-loop` implements an approved screen proposal in the screen's code.

## The mockup

- **Built from the screen's source, checked against the running app.** `design-refresh` reads the
  screen file and the local files that shape its layout (its layout wrapper, the page's own
  sub-components), and screenshots the screen on the dev server for comparison. Those files are
  the row's `sources`; data hooks, stores and kit components are not.
- **Same page model as a proposal** ([`proposals.md`](./proposals.md)): it loads the synced files
  by relative path (`../styles.css`, `../_ds_bundle.css`, `../_vendor/react.js`,
  `../_vendor/react-dom.js`, `../_ds_bundle.js`), renders the synced components from
  `window.<globalName>` inside the design provider's side-by-side mode (`mode="both"`), and never
  copies a component.
- **Layout in inline styles with the semantic tokens.** The bundle only compiles the Tailwind
  classes the kit uses, so the screen's own layout classes don't exist in the project. Translate
  them to `style` values with `var(--token)`.
- **Plain script, no build step**: `React.createElement` (as `h`), so Claude Design and
  `design-loop` read it as is.
- **Sample data, never real data.** Write invented content with the same shape, length and
  language as what the screen shows. Never copy names, emails, messages or documents from the
  dev app: the mockup is uploaded to Claude Design.
- **States.** The main state is what the dev server shows. Other states the user asks for (empty,
  loading, error, long content) come from the screen's source (its empty or error branch), one
  section each, marked `data-nav-section="<state>"` so the navbar lists them.
- **A header comment** says what the page is:

  ```html
  <!-- Mockup of <route>, generated by design-refresh from <sources> on <date>.
       Approximate layout; the components are the synced ones.
       Known differences: <what still differs from the app, or "none">.
       Propose a change in proposals/screens/<name>.html, not here: this page is regenerated. -->
  ```

The mockup is rebuilt from the code, so it is **read only** in Claude Design like the synced
cards. Before overwriting it, `design-refresh` checks it is unchanged since it was uploaded
(`mockupHash`); an edited mockup is a proposal someone made in the wrong place.

## A screen proposal

Lives at the row's `proposalPath`, `proposals/screens/<name>.html`: a copy of the mockup with the
change, in the same side-by-side mode. It may restructure the layout, restyle it with the
semantic tokens and recompose the synced components. It says what changed in its `<title>` or a
short note, and which state it is for. Its data is illustrative: `design-loop` implements layout
and styling, never data. A change to a kit component itself (a new Button variant) is a
component proposal.

## Rendering and screenshots

- **The app:** the screen's `url` on the dev server, one screenshot per mode, at the row's
  `viewport`:

  ```bash
  cd <dir> && node <screenshot.mjs> "<url>" /tmp/design-screens/<name>.app.<mode>.png \
    --viewport <viewport> --color-scheme <mode> [--storage-state <screensAuth>]
  ```

  An app that doesn't follow the OS mode needs its own switch for the dark capture; without one,
  capture light only and say so.

- **The mockup or a proposal:** copy the local `/design sync` output (`ds-bundle/`) to a temp
  directory, write the page at its project path inside it, and screenshot it with both panels at
  the screen's width: twice the viewport width plus the provider's padding and gap
  (`--viewport 2960x900` for a 1440x900 screen with the reference provider's 16px). Compare each
  half to the matching app screenshot. First check that the local bundle is the uploaded one
  (`bundleSha12`, as for proposals).
- **Sign-in.** For an app behind a login, record one once and keep it out of git:

  ```bash
  cd <dir> && node <screenshot.mjs> --save-auth "<url>" <screensAuth>
  ```

  Sign in in the window that opens, then click its "Save login" button. The file holds session tokens: git-ignore it,
  never upload or print it. Record it again when a screenshot shows the sign-in page.

## In the manifest

Each screen is a `screens[]` row (contract §2). `sourceHash` is the hash of its `sources`, in
order:

```bash
cat <sources…> | shasum -a 256 | cut -d' ' -f1
```

A mockup is stale when this differs from the row's `sourceHash`. Kit changes don't make it stale:
the mockup renders the synced components, so a sync updates them.

## The navbar and palette footer

The design provider loads the shared navbar only on `components/` and `proposals/` pages
([`proposals.md`](./proposals.md#side-by-side-modes-and-the-navbar-in-the-design-provider)). For
screens, add `screens` to its path check (`/^(components|proposals|screens)\//`), so the palette
footer can re-theme a screen live. The sidebar lists the screens under **Pages**, from
`screens/index.json` (Claude Design's card list doesn't include them): every upload of
`design-refresh` rewrites it from the manifest's `screens[]`.
